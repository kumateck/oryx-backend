# Post-issue material quantity corrections

Implemented locally on 2026-11-03. `IssuedMaterialRepairController` exposes
`PreviewIssuedMaterialRepair` and `ApplyIssuedMaterialRepair` at
`/api/v1/production-schedule/{batchId}/issued-material-repair/{kind}`; `kind=0`
repairs BOM quantities and `kind=1` packaging quantities. Both are typed operations
with stable operation IDs. No customer data or grants were changed.

Correct the source master through the existing editor first. Preview compares
the corrected full/half-batch requirement with exact issued reservations and
earlier corrections. The apply payload contains only `requestId`, `previewToken`
and an audit `reason`. The server derives and posts only the remaining delta.

`CanRepairIssuedBom` and `CanRepairIssuedPackaging` are separate catalog entries,
without automatic role grants. The service additionally requires the existing
production-board view permission, an active account, and the product's production
department. Access is checked again under the transaction and before saving.

The automatic path is for stock issued and still held in production. It requires
one approved, fully issued requisition with an unchanged material set, consistent
units, requisition-linked source bin cards, matching production reservations and
a reconciled source warehouse. Missing/ambiguous/deleted/consumed evidence,
started consumption, returns, extra-material requests, finalized packing/FG
transfers and finished/cancelled runs refuse without stock changes. These cases
require separate reviewed corrections; do not infer a historical issue from
similar quantities/timestamps or silently reverse consumption.

Increases use date-eligible available source lots, respecting other unissued
reservations and lot remaining balances. Decreases return unconsumed stock only
to a verified original physical shelf. A soft-deleted exhausted shelf allocation
stays deleted; the return creates a new allocation. No quality status, expiry,
retest date, total receipt or consumed quantity is changed.

A serializable transaction with write-conflicting table locks repeats all
evidence and availability checks and the preview fingerprint. It writes shelf
and reservation deltas, reconciles the affected batches' `QuantityAssigned`
summary to live shelves, and appends movements, batch events, source bin cards,
activity log and repair/line/allocation evidence. Audit allocations retain stock
and assigned-summary before/after values and reservation/movement/bin-card IDs.
Reasons and material code/name/unit snapshots remain on the immutable document.
The original approved requisition and approval stages are never overwritten.

`IssuedMaterialRepairRead` overlays accumulated corrections on requisition DTO
`Quantity`; `ApprovedQuantity` exposes the original signed amount. Both stock
requisition reads used by the production workflow and the warehouse detail use
this projection. Production stock/consumption already use the current reservation
rows. Material lots keep their valuation provenance; no new financial price or
journal is generated by this internal stock transfer.

The repair ID is the client request ID. An exact replay returns the original
receipt, conflicting reuse fails, and a newly requested repair after the current
target is reached makes no adjustment. A later corrected master creates only
its new delta. The DbContext and PostgreSQL triggers enforce append-only audit
tables, including refusing direct SQL DELETE/UPDATE/TRUNCATE. Concurrent or stale
writes return 409; clients must reload and review, without an automatic replay.

The repair advances the activity's existing `UpdatedAt` concurrency token.
Product Preparation/Final Packing starting from an older activity snapshot fails
its first atomic consumption save with 409; a fresh load consumes the corrected
reservations exactly once. Failed repair and step writes clear pending tracked
changes so later audit persistence cannot flush a refused stock plan.

Apply migration `20261103204140_AddIssuedMaterialRepairs` before deploying the
new read projection or UI. It adds three audit tables, indexes, foreign keys and
append-only triggers only. It is prepared locally and remains unapplied on
customer/main/rehearsal databases. The exact Up operations are exercised inside
the disposable acceptance fixture; EF reports no pending model changes.

Run local PostgreSQL acceptance with:

```sh
ORYX_ISSUE_REPAIR_TEST_CONNECTION='Host=localhost;Port=5432;Database=postgres;Username=LOCAL_USER' \
  dotnet test tests/APP.Tests/APP.Tests.csproj --filter FullyQualifiedName~IssuedMaterialRepairTests
```

Tests create/remove only local `oryx_issue_repair_test_<random>` databases. The
real warehouse issue operation reproduces PMF015=22.5 mg and PMF093=95 mg; after
the source master is corrected, the repair transfers 22,499,977.5 mg and
94,999,905 mg respectively. Coverage includes both kinds, increases/decreases,
repeat requests, stock shortages/expiry, other reservations, stale evidence,
access revocation/scope, protected history, rollback and concurrency. The actual
client incident and its downstream state still require a read-only live preview
and operational acceptance before any client repair is applied.
