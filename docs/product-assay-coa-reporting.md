# Product assay COA reporting

Each individual product specification can opt selected formula outputs into percentage weight/volume reporting. The identity is the product specification (which stores product and test stage), form-field ID, and stable formula result key. Template names, assay labels and shared specification numbers never select a rule. Multiple identically named assays and multiple outputs remain independent. Unconfigured products and outputs keep their existing reporting.

QC opens Product specifications, selects the individual product record, and chooses COA assay reporting. Each selected output requires a nominal concentration in % w/v, inclusive lower/upper % w/v limits, and display precision. For a percentage-of-label-claim source, the result is `source / 100 * nominal concentration`. For example, `101.39 / 100 * 2.4 = 2.43336% w/v`; a 2.32–2.52 range passes. Evaluate the unrounded converted value and round only for display; nonzero results never display as zero. The COA prints each configured output's explicit limits alongside its reported value.

The source remains intact. The server reuses its formula engine for legacy saved readings (including averages); governed worksheets use the pinned authoritative execution's exact result. Unsupported legacy formula structures need an approved formula revision. Outputs already declaring a different unit, missing readings, stale formula hashes, ambiguous specifications, unapproved settings and unavailable calculations cannot produce a converted certificate. No browser-posted calculated value is trusted.

Saving a reporting configuration requires a fresh context token, a change reason, a serializable transaction and current `CanEditProductAssayReporting` grants immediately before saving. Only the individual specification is updated. Its existing verification is cleared so the normal specification approval must run again. Rules are stored separately from shared-number updates. Stale rules remain visible and can be removed individually; they continue to block generation until corrected.

At product certificate submission the response captures the actor/time, specification/product/revision, field/output identifiers, source-answer ID/hash, source formula, original and converted values, nominal concentration, limits, precision and verdict. Later reporting edits do not alter that snapshot. Existing already-submitted tests without a reporting snapshot preserve their original interpretation. Correcting/retesting a worksheet creates a new response through the existing workflow. Converted-output verdicts are enforced by the API even if a client omits or overrides its legacy compliance payload. The existing approval and release workflows remain in place.

GET/PUT `/api/v1/product-specifications/{id}/assay-reporting` require respectively `CanViewProductAssayReporting` and `CanEditProductAssayReporting`, under Quality Control / Product Specification. Both keys are registered separately. The companion grant migration copies view access types from existing specification viewers/editors/verifiers/creators and edit access types from existing specification editors. There are no role-name bypasses. Other accounts require explicit assignment.

The commercial COA register carries the captured reporting results and limits into its immutable certificate rows. Product certificate generation reloads the existing `CanCheckProductTest` grant inside its transaction and immediately before saving.

COA references use each test section’s saved specification reference, falling back to its question reference. Stored codes are displayed as BP, USP, Ph. Int. or In-house; a literal citation such as BP 2024 is preserved without inventing a year. References owned by a different specification number are excluded when a template is reused. Products linked to the same specification number retain their existing shared references. The commercial certificate stores the resolved reference when issued, so later template edits cannot alter that certificate.

Legacy conversion requires the existing server formula calculation service to be enabled and reachable; an unavailable service blocks conversion with a review message. Deploy the schema/grant migration and backend before activating the companion desktop. No application database is migrated by this task.

## Verification

The focused backend regression suite passed 66 tests, including permissions, product/output isolation, captured and historical behavior, specification approval, missing/stale calculation failures, precise rounding, server enforcement with omitted/overridden client compliance, issued COA preservation and reference scope. This includes real formula-engine evaluation and schema/grant/concurrent-update tests on an isolated local PostgreSQL database. Five optional pre-existing formula-repair integration tests were skipped because their separate environment variables were not configured. The new assay integration tests were run, not skipped.

The API/test projects build, the permission catalog checks pass, and EF reports no model changes since the added migration. The companion desktop passed 48 focused tests, 43 additive-contract review tests, all workspace typechecks, API/route checks and the production web build. Browser checks covered settings and editor at 1366×768, 1280×720, 1024×576 and 854×480 and a COA preview showing the converted result with its BP reference. No deployment or application database migration was performed.
