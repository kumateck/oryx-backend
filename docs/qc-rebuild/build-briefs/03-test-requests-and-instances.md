# Milestone 3: TestRequest + WorksheetInstance (Execution)

Status: not started. Depends on Milestone 1
([01-stp-and-worksheet-templates.md](./01-stp-and-worksheet-templates.md)) and
Milestone 2 ([02-specifications.md](./02-specifications.md)). `CalculatedValue`
evaluation uses the new local evaluator resolved by
[00-formula-engine-spike.md](./00-formula-engine-spike.md) — nothing to stub.

## Objective

Deliver `TestRequest` (the ARD) and `WorksheetInstance` (execution) end to end:
creating a test request against a Specification, generating the required worksheet
instances, the Test Room ("My Work") and review queue UI, assignment enforcement,
header-block auto-rendering, `ReferencedResult` runtime resolution, and the hard
instrument/reagent gates. This milestone does **not** include `OosCase` (Milestone
4) or `Coa` generation (Milestone 5) — a `WorksheetInstance` reaching `Submitted`/
`Reviewed` is as far as this milestone goes; what happens on a failing result, and
how a released `TestRequest` becomes a certificate, are the next two milestones.

## Do-not-touch boundary

Same as prior milestones — new code only, under `DOMAIN.Entities.QcWorksheets`,
`api/v{version}/qc/worksheets/...`, `qc/worksheets/...`. This milestone reads (never
writes) two existing tables: `QcEquipment` (for Instrument-field calibration checks)
and `Reagent` (for the reagent-type dropdown, name/description only — batch number
and expiry are captured fresh per worksheet, not read from `Reagent`). Do not modify
either. See
[README.md](../README.md#the-existing-materialproductpackaging-system-is-mature-not-shelved--and-the-new-module-coexists-with-it).

## Design resolution: a TestRequest covers multiple subjects

[domain-model.md](../domain-model.md) states a `TestRequest`/round "may cover
multiple sampling points/subjects," matching the real Environmental Monitoring
worksheet (~90 rooms in one round) and Water worksheet (15+ points in one round) —
but the entity as written only had a single scalar `SubjectRef`, which can't
represent that. Resolved here by introducing `TestRequestSubject` as an explicit
child entity, mirroring the existing `RoutineExecution -> RoutineSample` nesting
this design was always meant to match:

```
TestRequest                              // the round
  Type: enum { RawMaterial, PackagingMaterial, Product, RoutineWater,
      RoutineEnvironmental }   // mirrors Specification.AppliesTo
  SpecificationId + SpecificationVersion (pinned at creation — shared by every
      Subject in the round, since one round tests against one Specification)
  ScheduleOrigin: enum { Scheduled, Unscheduled }
  UnscheduledReason: string?    // required by application-layer validation when
                                  // ScheduleOrigin = Unscheduled, not a DB constraint
  ArNumber: string (required, max 100)      // round-level AR number
  IssueNumber: string? (max 100)
  IssuedAt: DateTime?
  IssuedById: Guid?
  Status: enum { Draft, Sampled, Assigned, InTesting, ResultsComplete, UnderReview,
      Released, Rejected }
  Subjects: List<TestRequestSubject>

TestRequestSubject                       // one per batch (Material/Product,
                                          // normally exactly one per TestRequest) or
                                          // one per sampling point (Water/EM,
                                          // normally many per TestRequest)
  TestRequestId: Guid (required)
  SubjectRef: string (required, max 200)   // batch number, or sampling point code
                                             // e.g. "SF-91"
  SubjectLabel: string? (max 500)           // e.g. "Deblistering-2" — the human name
                                             // alongside the code, per real EM sheets
  ArNumber: string? (max 100)               // per-point AR sub-number — confirmed on
                                             // the real Water worksheet, where each
                                             // point gets its own AR number nested
                                             // under the round's AR number
  SamplingPointGroupId: Guid? (FK to SamplingPointGroup — Water/EM only, drives
      which Alert/Action tier a submitted Result is checked against)
  SamplingPointId: Guid? (FK to SamplingPoint — Water/EM only; added retroactively,
      see build-briefs/06-monitoring-programs-and-water-quality.md — auto-populated
      when system-generated by a MonitoringProgram, optional for manually-added
      unscheduled Subjects)
  MaterialBatchId: Guid? (FK to the existing MaterialBatch entity — Material only;
      added retroactively, see build-briefs/04-oos-cases.md — OOS quarantine needs
      a real batch to act on, not just the SubjectRef string)
  BatchManufacturingRecordId: Guid? (FK to the existing BatchManufacturingRecord
      entity — Product only, same reason)
  CollectedAt: DateTime?
  WorksheetInstances: List<WorksheetInstance>

WorksheetInstance : BaseEntity, IRequireApproval   // one per required worksheet, per Subject
  Approved: bool   // looked up via the shared QcApproval table (Milestone 1),
                    // EntityType = "WorksheetInstance"
  TestRequestSubjectId: Guid (required)
  WorksheetTemplateId: Guid (required)
  WorksheetTemplateVersion: int (required)   // pinned at creation
  AnalysisType: enum { Chemical, Microbial }
  AssignedToId: Guid?
  AssignedById: Guid?
  AssignedAt: DateTime?
  RetestOfInstanceId: Guid?     // set only by Milestone 4's OOS retest flow — this
                                 // milestone defines the column and never writes to
                                 // it itself
  Status: enum { NotStarted, InProgress, Submitted, Reviewed, Locked }
  FieldValues: List<WorksheetFieldValue>

WorksheetInstanceReassignment             // plain audit record, not an Approval —
                                            // reassignment is administrative, not a
                                            // sign-off (see lifecycle-and-governance.md's
                                            // assignment-enforcement rule)
  WorksheetInstanceId: Guid (required)
  FromUserId: Guid?             // null if reassigning an unassigned instance
  ToUserId: Guid (required)
  ReassignedById: Guid (required)
  ReassignedAt: DateTime (required)
  Reason: string (required, max 1000)

WorksheetFieldValue
  WorksheetInstanceId: Guid (required)
  FieldKey: string (required)              // the WorksheetField's FieldKey
  RowIndex: int?                            // null for a scalar field; 0-based row
                                             // number when FieldKey belongs to a
                                             // Table field
  ColumnKey: string?                        // null for a plain scalar value;
                                             // set for Table cells (matches a key in
                                             // the field's ColumnDefinitions), and
                                             // also used for the composite
                                             // Reagent/ReferenceStandard value shape
                                             // below (ColumnKey = "reagentId" |
                                             // "batchNo" | "expiryDate")
  Value: string (required)
  EnteredById: Guid (required)
  EnteredAt: DateTime (required)
  ResolvedFromInstanceId: Guid?              // set only for ReferencedResult fields
```

`RequiredWorksheets` from [domain-model.md](../domain-model.md) isn't a stored list —
it's resolved once, at `TestRequest` creation, from `Specification.WorksheetLinks`,
and materializes as one `WorksheetInstance` per `(TestRequestSubject ×
WorksheetLink)` pair. If the linked Specification has both a Chemical and a
Microbial `WorksheetLink`, every `TestRequestSubject` gets two `WorksheetInstance`s.

## Reagent/ReferenceStandard field value shape

A `WorksheetField` of `Type = Reagent` or `ReferenceStandard` stores its entered
value as **three** `WorksheetFieldValue` rows sharing the same `FieldKey` (and
`RowIndex` if the field is inside a Table), differentiated by `ColumnKey`:
`"reagentId"` (a `Reagent` FK, read-only catalog lookup), `"batchNo"` (free text),
`"expiryDate"` (date). The hard expiry gate (see below) checks `expiryDate` against
today — the value just entered, not a master-data record — because no existing
entity tracks reagent-lot expiry; the real worksheets capture it fresh each time
too, confirmed against the Cetrimide worksheet's "Date of Expiry" field.

An `Instrument`-type field stores a single `WorksheetFieldValue` whose `Value` is a
`QcEquipment` id. The hard calibration gate reads that `QcEquipment` row's
`CalibrationDueDate` directly — a real master-data lookup, unlike Reagent.

## Header block rendering

`GET /{id}` on `WorksheetInstanceController` computes, never stores:

```
BatchNo / SamplingPointCode  <- TestRequestSubject.SubjectRef
ArNumber                     <- TestRequestSubject.ArNumber ?? TestRequest.ArNumber
SpecNo + Revision            <- Specification.Code + "Rev " + Specification.Version
                                 (resolved via TestRequest.SpecificationId +
                                 SpecificationVersion — the PINNED version, not
                                 whatever is currently Effective)
StpNo                        <- WorksheetTemplate.StpId -> StandardTestProcedure.Code
                                 (resolved via the WorksheetTemplate's PINNED
                                 version's StpId, not the current one)
IssueNo / IssuedAt / IssuedBy <- TestRequest fields
Mfg/Exp dates                <- TestRequestSubject fields where applicable
                                 (Material/Product only; blank for Water/EM)
SampledOn                    <- TestRequestSubject.CollectedAt
AnalysisDate                 <- WorksheetInstance.AssignedAt .. Submitted timestamp
```

This is what every real filled ARD reviewed in Phase 1 prints as a fixed header —
render it, never let an analyst type into it.

## ReferencedResult runtime resolution

When `GET /{id}` encounters a `WorksheetField` of `Type = ReferencedResult`:

1. Read the entered value of `ReferencedResultResolutionFieldKey` on this same
   instance (e.g. the paired Reagent field's `batchNo` — the analyst has to enter
   that before the referenced value can resolve; render the `ReferencedResult`
   field as pending/unresolved until then, not as an error).
2. Query `WorksheetInstance` where `WorksheetTemplateId = ReferencedResultSourceTemplateId`
   AND the target instance's own `batchNo`-equivalent field value matches the
   resolution value from step 1, AND `Status = Reviewed` (only a reviewed, not
   merely submitted, source result should be trusted) — most recent match if
   several exist.
3. If found: populate the field read-only with the source's
   `ReferencedResultSourceFieldKey` value, set `ResolvedFromInstanceId`, and make it
   a clickable link (per [test-room-ux.md](../test-room-ux.md#referenced-fields)).
4. If not found: render clearly as unresolved ("No matching qualification found for
   batch X") — do not block the rest of the worksheet, but this field cannot be
   submitted as part of `/submit` until it resolves.

## Hard instrument/reagent gates

Enforced in `PUT /{id}/values` before persisting any value on a gated field, and
again in `POST /{id}/submit` as a final check (defense in depth — a value could
theoretically become stale between entry and submission if calibration data
changes):

- **Instrument field**: look up the entered `QcEquipment` id's `CalibrationDueDate`.
  If it's in the past, reject the write with a clear error naming the equipment and
  the due date. No override path in this milestone.
- **Reagent/ReferenceStandard field**: check the entered `expiryDate` sub-value
  against today. If expired, reject the write the same way.

## Acceptance criteria

1. **Multi-subject round**: Create a `TestRequest` (Type = RoutineEnvironmental)
   with 5 `TestRequestSubject`s. Verify 5 `WorksheetInstance`s are created (one per
   subject, Microbial only per the Specification's WorksheetLinks).
2. **Assignment enforcement**: Assign a `WorksheetInstance` to User A. Log in as
   User B (who holds `CanStartMicrobialWorksheet`) and attempt `/start`. Verify
   rejection despite holding the permission key.
3. **Reassignment preserves entered values and is audited**: Enter a field value
   as User A. Reassign to User B. Verify the existing `WorksheetFieldValue.EnteredById`
   is still User A, not rewritten to User B, and a `WorksheetInstanceReassignment`
   row exists with `FromUserId = A`, `ToUserId = B`. Verify no `QcApproval` row was
   created for this action — reassignment is not routed through the Approval engine.
4. **Header block is never editable**: Verify no API path lets a client set
   `TestRequestSubject.SubjectRef` or `Specification.Code` through the
   `WorksheetInstance` values endpoint — the header is GET-only, computed.
5. **Instrument gate**: Configure a `QcEquipment` row with `CalibrationDueDate` in
   the past. Attempt to enter it as an Instrument-field value. Verify rejection.
   Update `CalibrationDueDate` to the future. Verify the same entry now succeeds.
6. **Reagent gate**: Enter a Reagent-type field value with `expiryDate` in the
   past. Verify rejection with today's date. Enter one with a future date. Verify
   success.
7. **ReferencedResult resolves only against Reviewed sources**: Create a source
   MediaQualification `WorksheetInstance` at `Status = Submitted` (not yet
   Reviewed). Verify a dependent `ReferencedResult` field does not resolve.
   Transition the source to `Reviewed`. Verify it now resolves.
8. **Coexistence**: Existing `qc/routines/*`, `qc/analytical-raw-data`, and
   `qc/product-analytical-raw-data` pages still load and function unchanged.
